# Open question: expected office scope for Fineract client documents

**Status:** Public research question; not sent to the Fineract security team before publication.<br>
**Tested branch:** Apache Fineract `develop` commit `b033c13637123574a2242e39ce5e6aef29f58fdb`, checked against the remote branch on 2026-11-27 (KST).<br>
**Environment:** macOS 15.0.1 arm64, OpenJDK 25.0.5.0.3, PostgreSQL 16.15, fresh empty master and tenant databases migrated by Fineract, default Basic authentication, loopback HTTPS. No test profile or third-party deployment. A local Docker VM error required a temporary Gradle codegen adapter that used a disposable local PostgreSQL database to generate QueryDSL sources from this exact HEAD. The adapter was restored before the product source was compiled and run; the checkout was clean during the final reproduction.

## Policy question

Are `READ_DOCUMENT`, `UPDATE_DOCUMENT`, and `DELETE_DOCUMENT` intended to grant access to **every** client document in a tenant, including clients in unrelated offices? Or should document access follow the same office hierarchy as client detail access? The architecture document states the general office hierarchy rule but does not explicitly list the document API. This answer determines whether the observed cross-office access is a broken authorization boundary or an intended global permission.

Independently, should `PUT` and `DELETE /api/v1/clients/{clientId}/documents/{documentId}` reject a `{clientId}` that is not the document's actual parent? The matching GET rejects that mismatch, but the write service looks up only `{documentId}`.

## Reproduction in a controlled sandbox

1. On the fresh default tenant, create sibling offices A and B, one synthetic client and a synthetic PNG document in each. Create a non-admin A-office update user with exactly `READ_CLIENT`, `READ_DOCUMENT`, `UPDATE_DOCUMENT`; create a second A-office delete user with exactly `READ_CLIENT`, `READ_DOCUMENT`, `DELETE_DOCUMENT`. An administrator acts only during fixture creation.
2. With each limited user's own Basic credentials, enumerate synthetic client IDs 1–16 via `GET /api/v1/clients/{id}/documents`. The B client at ID 2 returns a list of document IDs. `GET /api/v1/clients/2` returns `404`, while the B document metadata and attachment return `200`.
3. With the update user, send a metadata-only `PUT /api/v1/clients/2/documents/3`: HTTP `200`, and the B document name changes. With the delete user, send `DELETE /api/v1/clients/2/documents/4`: HTTP `200`; subsequent document GET is `404`, and the pre-existing file and database row are absent. These are the **correct B-client paths**. Both users can also update or delete documents in their own A office as positive controls.

## Limits relevant to triage

The default non-admin role has no document permissions; the two document roles above were explicitly created for the test. The scan covered only 16 synthetic customer IDs and does not establish the rate, scale, or role prevalence in financial deployments. No real customer information, external service, or other tenant was accessed. The external OIDC path was also reproduced on this exact `b033c1363…` HEAD with a synthetic issuer: [Bearer HTTP observations](lab/evidence/document_office_scope_b033_oidc_write_20261127.json) and [runtime provenance](lab/evidence/document_office_scope_b033_oidc_provenance_20261127.json). Basic-only API requests received `401` in that mode. With Basic fully disabled, the same HEAD fails to start because no `PasswordEncoder` bean is available: [startup evidence](lab/evidence/document_office_scope_b033_oidc_only_startup_20261127.json). The official 1.16.1 JAR also allowed the document actions, but an additional, publicly patched nested-path permission bypass exists in that release; we do not present it as the same residual issue. No severity or CVE assignment is requested before the intended permission scope is confirmed.
